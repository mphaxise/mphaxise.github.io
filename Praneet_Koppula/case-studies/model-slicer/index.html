01 · The idea

As logic moved into diagrams, verification had to move with it.

Simulink gives engineers an executable map of a system. Blocks represent components or equations; arrows carry signals between them. Teams can simulate that model, test it, and generate implementation code from it.

The visual map remains hard to reason about when it grows across deep hierarchies and many modes. Program slicing had long helped software engineers reduce code to the statements related to one behavior. Model Slicer applies a similar focusing idea to executable block diagrams.

The surrounding safety environment raised the standard for model-level evidence. FAA guidance recognizes DO-331 for model-based development and verification, while ISO 26262 covers software and system verification in road vehicles. These standards do not prescribe Model Slicer. They show why the model itself had become a verification artifact.

Try the core idea: focus a large dependency network around one failing signal.

Whole model
The diagram is visible. The causal path is crowded.

A slice keeps the blocks and dependencies relevant to one behavior so an engineer can inspect a smaller, explainable surface.

Public framing: MathWorks describes Simulink models as block-diagram representations of systems and Model Slicer as a way to understand dependencies in large or complex models. Program slicing supplies the conceptual lineage. Sources are collected at the end.

01 / USABILITY

Make the MVP usable enough to evaluate.

A small set of labels hid a large state machine. Starting points, exclusions, constraints, generated slices, and source navigation all needed predictable rules.

I mapped Model Slicer actions to the state of the selected block or signal. The interface had to know whether an object already played a role, whether multiple objects were selected, and whether a new action conflicted with the current configuration.

A context-menu deck and a detailed enable/disable matrix made those rules inspectable. I developed the interaction details with an engineering partner. Our team's usability plan covered real slicing tasks, including highlighting dependencies and generating a smaller model.

  • Selection
    Offer actions that fit the object.

    Blocks, signals, conditional elements, and multi-selections needed different valid choices.

  • Conflict
    Give roles a clear precedence.

    An object could not behave as both an exclusion and a starting point. The product needed a predictable resolution.

  • Recovery
    Keep a path back to the source.

    Users needed to move between the focused slice and the original model without losing context.

02 / DYNAMIC SLICING

Make a slice trustworthy over time.

Static slicing asks which blocks could affect a result. Dynamic slicing asks which blocks affected it during a particular execution and time window.

My 2015 prototypes explored two paths: load existing coverage data or run a simulation, then refine the highlighted slice within a selected interval. The interaction had to expose where the data came from, when it was recorded, and whether the requested time window was valid.

I separated Refine from Simulate and refine. That choice told users when the current data could support an answer and when changed inputs or workspace variables required a fresh simulation.

  • Data
    Show the source of behavior.

    Loaded coverage and a new simulation represented different evidence states.

  • Time
    Constrain the interval to recorded results.

    The product surfaced the available range and rejected a request beyond it.

  • Action
    Name when recalculation was required.

    Distinct actions made stale inputs and simulation state visible.

03 · Integration

Put slicing where failures already appeared.

The early releases established the core interaction. The next product question was discoverability: how could engineers reach a focused slice from the verification result they were already trying to understand?

I worked with teams across Simulink Test, coverage, Simulink Design Verifier, and Model Slicer to shape those cross-product flows. Public documentation later records the team-owned integrations that shipped from R2020b through R2022a.

Workflow A

From a failed test to the responsible model path.

Test data from a rig, baseline, or earlier system state can reveal a mismatch. The integrated workflow carries that signal into Model Slicer.

  1. 01
    Run model or code test
  2. 02
    Select the failed signal
  3. 03
    Launch Model Slicer
  4. 04
    Trace the active dependencies
  5. 05
    Fix the model and rerun

MathWorks now documents this pattern in Test Manager: select a failed result, launch a slicer debugging session, move to the failure region, and inspect the highlighted dependency chain.

Workflow B

From a generated objective to the logic that explains it.

Design Verifier can detect conditions such as division by zero, dead logic, integer overflow, and array-access violations, then generate tests that exercise difficult behavior. Model Slicer makes the path to the result inspectable.

  1. 01
    Generate test objectives
  2. 02
    Select an objective
  3. 03
    Inspect using Slicer
  4. 04
    Pause at observation time
  5. 05
    Read values and paths

The workflow turns a formal-analysis result into a focused explanation inside the model, close to the algorithm that needs attention.

04 · Outcome

The product arc expanded where slicing could create value.

Model Slicer progressed from a capability an expert had to find and configure into a workflow that could begin with a failed test or verification objective.

  • Early release
    A usable path toward customer validation.

    I addressed release-critical interaction issues to prepare the early automotive partner evaluation.

  • Workflow depth
    A slice grounded in state, data, and time.

    Dynamic slicing exposed the evidence behind a highlighted result and the conditions that could invalidate it.

  • Product reach
    A focused explanation at the moment of failure.

    Public R2020b–R2022a integrations place Model Slicer inside testing and formal-verification journeys across product boundaries.

05 · What stayed with me

Complex tools become clearer when the product exposes its reasoning.

  1. 01
    Discovery is a workflow decision.

    Place a specialist tool at the moment a user encounters the problem it can solve.

  2. 02
    State is part of the interface.

    Data source, validity, timing, constraints, and recovery shape trust as much as the visible controls.

  3. 03
    Prototype the disagreement.

    A useful prototype makes functional conflicts concrete while the team can still resolve them cheaply.

The six-year shift
A failed test became an entry point to the model behavior that explained it.

The story began with a narrow release goal: help an early customer use a promising capability. It grew into a broader product pattern for connecting verification evidence to an understandable slice of a complex system.
