Agentic redesign begins with the system you already have

A stronger product emerges when user needs, current client behavior, and verified backend behavior guide the same redesign.

By Praneet Koppula6 min readJuly 2026

The existing product is the first design artifact.

Agentic redesign begins with the system people already depend on. The work starts by understanding what people are trying to do, what the current client actually does, and what the backend can reliably support.

That shared model gives a designer and an implementation agent enough truth to improve the experience while preserving behavior people trust. It also exposes missing capabilities early, when the team can turn them into explicit product work.

01
Orientation

Begin with the operating product

A redesign inherits a living system. People have learned its sequence, its language, and its ways of recovering from mistakes. The client contains years of product decisions. The backend enforces its own contracts, permissions, timing, and failure behavior.

An agent can move through that material quickly. It can trace routes, inspect components, follow requests, compare states, and build a candidate change. Speed becomes useful when the work has a clear factual base.

I start by placing three views of the product beside one another:

  1. User needs: the goal, context, expectations, and points of uncertainty people bring to the flow.
  2. Client behavior: the screens, states, local logic, validation, navigation, and recovery paths people experience today.
  3. Backend behavior: the verified data contracts, permissions, side effects, error conditions, and response timing that shape what the product can do.

Each view answers a different question. Together they reveal the actual design space.

A polished concept built from one view can quietly conflict with the other two. A new control may imply that a change happens immediately while the API processes it in a batch. A simplified form may hide a field the server requires. A seamless transition may erase the moment when a person needs to confirm a consequential action.

The operating product makes those constraints visible. It gives the redesign somewhere honest to begin.

02
Evidence

Build a verified behavior model

The redesign needs a compact model of how the product behaves before the interface changes. This model can be lightweight. Its value comes from verification.

I ask the agent to trace one real task from entry to completion. For every meaningful step, we record what the person sees, which state the client holds, which request the system makes, what the backend returns, and how the experience responds when something goes wrong.

Running the current product supplies part of the evidence. Reading the client and server code supplies another. Tests, logs, schemas, and direct calls can confirm the details. When those sources disagree, the disagreement becomes a finding for the team.

The resulting behavior model might be a short flow map, a state table, or a set of annotated scenarios. It should answer practical design questions:

  • Which behavior is intentional and which is incidental?
  • Where does the client know the truth, and where is it waiting for the server?
  • Which actions are reversible?
  • What does the system do with partial, stale, or invalid data?
  • Which permissions change the experience?
  • How can a person tell that an action succeeded?

Unknowns stay visible. The agent can help investigate them, and the team owns the decision about how to resolve them. A verified map gives everyone the same product to redesign.

03
Delivery

Redesign one coherent slice

A coherent slice improves a complete piece of the experience across interface, state, system behavior, and recovery. It is small enough to verify and complete enough for a person to use.

The slice begins with a user outcome. A person may need to understand a status, change a preference, resolve an error, or approve an action. The current behavior model shows which parts of the system participate in that outcome. The redesign can then change those parts together.

Consider a generic settings flow. The current interface collects several edits and saves them with one final action. Research shows that people lose track of unsaved changes. The backend accepts only a complete settings object and validates several fields together.

A coherent redesign can make edited fields visible, keep the save action present, explain validation near the affected input, and preserve a clear success state. An implementation agent can carry the change through components, state handling, request construction, and tests. The existing backend contract remains intact.

This approach creates a fast design-and-build loop:

  1. Define the user outcome and trusted behavior to preserve.
  2. Give the agent the verified flow, system constraints, and acceptance scenarios.
  3. Build the smallest complete change in the running product.
  4. Use the result as a designer and as a person encountering each key state.
  5. Run product, accessibility, and regression checks.
  6. Revise from observed behavior.

The running product becomes the shared design surface. Critique can address the exact moment where layout, language, data, and behavior meet.

04
Product work

Turn capability gaps into product work

Some experience improvements require capabilities the product does not have. The redesign process should surface those gaps with enough precision for the team to act.

In the settings example, automatic saving could reduce uncertainty. The existing API still requires a complete object and validates related fields as a group. The concept has uncovered a product capability: safe partial updates with clear conflict, validation, and recovery behavior.

That gap belongs in the product plan. The team can define the user value, backend contract, security and permission implications, migration needs, failure states, and measurements. Design can show how the capability should feel. Engineering can determine how to support it safely. Product can decide when it earns priority.

The current redesign can proceed within verified system behavior. A later slice can introduce automatic saving after the capability exists and its risks have been resolved.

Agents make gaps easier to discover because they can follow a proposed interaction into the implementation. Their fluency can also make an unsupported idea look plausible. Explicit capability work keeps the proposal connected to reality.

Trust is the measure of the redesign

People build trust through repeated encounters with understandable behavior. They learn what an action will do, when the system is working, what went wrong, and how to recover.

A successful redesign improves that relationship. It can simplify a flow, clarify state, reduce effort, or introduce a stronger interaction model. It also preserves the product behaviors that remain useful and dependable.

Agentic tools help designers inspect more of the system and carry a decision further into working software. Human judgment still defines the outcome, chooses the evidence, resolves tradeoffs, and decides when the result is safe to use.

The existing product gives that judgment something concrete to work with. Its user needs, client behavior, and backend behavior form the ground for every coherent change.

A practical principle

Improve the experience from inside the system that produces it.

Verify the current behavior. Choose a complete slice. Build through the real client and backend contract. Turn missing capabilities into named product work. Then use the running result to guide the next decision.
